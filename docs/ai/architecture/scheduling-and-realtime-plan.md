# 调度与实时推送方案

> 目标：把「状态正确性」从定时任务中解耦，并用服务端推送替代前端轮询。
> 状态：方案设计（未修改代码）。

## 1. 背景与目标

### 现状问题

当前用 APScheduler 在 API 进程内周期性扫描，处理会员卡过期、课程自动完成、人数不足自动取消等。随着租户与数据量增长，暴露出可靠性、实时性与可观测性问题。

### 目标

1. 业务状态（是否过期、是否完成、是否可取消）**由数据本身推导**，不依赖任务是否执行成功。
2. 定时任务只承担**副作用**（通知、扣次、退款），且支持多实例、可重试、可审计。
3. 前端能**被动收到变更**，不必手动刷新。

### 非目标

- 不做实时协同编辑、不做双向消息（第一期只需服务端 → 客户端）。
- 不引入重型工作流引擎（Temporal / DBOS），除非后续需要跨天多步编排。
- 不修改核心业务规则（扣次、取消、退款语义保持不变）。

## 3. 问题清单

| # | 问题 | 影响 |
|---|---|---|
| 1 | 调度器与 API 同进程，无分布式锁 | 扩到多实例后同一 job 重复执行，结论依赖条件更新的侥幸 |
| 2 | 重启/部署/崩溃期间到点事件丢失 | 无补偿机制，只能等下次扫描顺带补，顺序不确定 |
| 3 | 全租户 + 全表按时间条件扫描 | 成本随时间线性增长，慢查询风险 |
| 4 | 状态存在窗口延迟 | 最长一个扫描周期内数据与事实不一致 |
| 5 | 无执行记录、无重试、无告警 | 连续失败无人知晓 |
| 6 | 租户上下文手工 `set_tenant_id` | 漏设导致查不到数据或退化为全表 |
| 7 | 业务规则写在任务里 | 难以单测，只能靠 sleep 验证 |
| 8 | 状态变更后前端无感知 | 用户必须手动刷新 |

### 核心判断

**问题不在"用了定时器"，而在"定时器承担了业务状态的正确性"。**

- 状态真相应从数据推导（如 `expire_at <= now()`），是纯函数；
- 定时器只负责"到点做某件有副作用的事"。

项目里的正面例子：`display_status` 按时间派生，任务全挂也不影响展示正确性。
反面例子：卡 `status` 依赖 `auto_expire_membership_cards` 改写，任务失败则字段长期说谎。

## 4. 三种方案

### 方案 A：惰性派生 + 读时校正

**核心**：查询时按当前时间计算状态；必须落库的状态在读到的瞬间做条件更新。

```sql
UPDATE membership_cards
SET status = 2, updated_at = now()
WHERE id = :id AND status = 1 AND expire_at <= now();
```

派生规则示例：

| 状态 | 派生方式 |
|---|---|
| 卡是否过期 | `expire_at <= now()` |
| 排期是否已结束 | `end_at <= now()` |
| 排期是否进行中 | `start_at <= now() < end_at` |
| 预约是否可取消 | `now() < start_at - cancel_before` |
| 预约展示状态 | 时间优先，其次才是 `booking.status`（已实现） |

| 维度 | 评价 |
|---|---|
| 实时性 | 强一致，无窗口 |
| 定时器 | 完全不需要 |
| 成本 | 仅在访问时发生，天然稀疏 |
| 局限 | 长期无人访问的数据不会更新，报表/统计需兜底 |

**适用**：会员卡状态、排期状态、预约展示状态。

### 方案 B：延迟消息 / 事件驱动

**核心**：事件发生时投递一条"到点执行"的任务，替代周期扫描。

```
预约创建 / 排期创建
   → 投递 job：run_at = end_at + grace_minutes，key = booking:{id}:complete
   → 到点消费：校验前置条件 → 执行副作用 → 标记 done
预约取消 / 排期变更
   → 撤销或覆盖原 job（以 key 幂等）
```

实现选项：

| 实现 | 引入成本 | 说明 |
|---|---|---|
| Redis ZSET 延迟队列 | 低（已有 Redis） | `ZADD` 时间戳，worker `ZRANGEBYSCORE` 捞到期任务 |
| RabbitMQ TTL + DLX | 中 | 成熟，需新增中间件与运维 |
| RocketMQ 延迟消息 | 中 | 原生多级延迟 |
| Celery / ARQ ETA | 中 | 需独立 worker 进程与部署编排 |

| 维度 | 评价 |
|---|---|
| 实时性 | 准点（秒级） |
| 成本 | 只处理受影响实体，O(1) |
| 依赖 | 必须设计幂等键与重试上限 |

**适用**：课程结束自动完成、开课前人数不足自动取消、卡到期提醒。

### 方案 C：任务表 + `SKIP LOCKED` Worker（含 Outbox）

**核心**：待执行的事落库，worker 抢任务执行，多实例安全。

```sql
SELECT id, type, payload
FROM job_queue
WHERE status = 'pending' AND run_at <= now()
ORDER BY run_at
LIMIT 20
FOR UPDATE SKIP LOCKED;
```

建议表结构：

| 字段 | 说明 |
|---|---|
| `id` | 主键 |
| `tenant_id` | 租户隔离必填 |
| `type` | 任务类型枚举 |
| `idempotency_key` | 唯一索引，防重复 |
| `payload` | JSON |
| `run_at` | 计划执行时间 |
| `status` | pending / running / done / failed / dead |
| `attempts` / `last_error` | 重试与排障 |
| `locked_by` / `locked_at` | 租约，超时可回收 |
| `created_at` / `updated_at` | 审计 |

| 维度 | 评价 |
|---|---|
| 可靠性 | 可重放、可审计、可暂停 |
| 扩展性 | 多实例靠 `SKIP LOCKED` 天然互斥 |
| 一致性 | Outbox 保证「业务提交 → 事件必达」 |
| 成本 | 仍有一个 tick，但只是队列消费者，不做业务扫描 |

**适用**：需要审计与可回放的任务，尤其是发通知、扣次等副作用。

### 方案关系

三种方案不是替代关系，而是分工：

- **A** 保证"看到的状态是对的"；
- **B** 保证"该发生的副作用准点发生"；
- **C** 保证"副作用不丢、可重试、可审计"。

## 5. 场景映射

| 业务场景 | 状态正确性 | 副作用与推送 |
|---|---|---|
| 会员卡过期 | A：`expire_at` 派生 + 读时条件更新 | 每日对账兜底；状态变更事件推送 |
| 排期状态（未开始/进行中/已结束） | A：纯时间派生，不落库 | 无需推送，前端本地按时钟计算 |
| 上课自动完成 | A 展示 + B 触发写状态 | 完成后推送学员/教师 |
| 人数不足自动取消 | A 展示 + B 触发取消 | 取消事件推送 + 微信订阅消息 |
| 卡到期提醒 | 无状态变更 | C：按日生成任务，幂等发送 |

## 6. 实时推送

### 选型

| 方式 | Web 三端 | 小程序 | 结论 |
|---|---|---|---|
| SSE | ✅ | ❌ 无 `EventSource` | Web 端首选 |
| WebSocket | ✅ | ✅ `uni.connectSocket` | 小程序首选 |
| 长轮询 | ✅ | ✅ | 兼容兜底 |

### 长轮询是什么

客户端发起请求后，服务端**不立即返回**，而是 hold 住直到有数据或超时（如 30s）；客户端收到响应后立即再发下一次请求。本质仍是 HTTP 请求—响应，只是把等待挪到服务端。

### 为什么不是"只用一个"

| 端 | 推荐 | 原因 |
|---|---|---|
| 管理端 / 学员端 Web | SSE | 纯 HTTP、浏览器内置自动重连、无需协议升级与额外端口 |
| 小程序 | WebSocket | 微信不支持 `EventSource`，`uni.connectSocket` 是唯一长连接方案 |
| 老浏览器 / 代理拦截流式 | 长轮询 | 兜底，保证功能不缺失 |

### 三个必须提前确认的点

1. **`EventSource` 不支持自定义 Header**：JWT 不能放 `Authorization`。方案二选一：
   - 用 Cookie 承载会话；
   - 用 `fetch` + `ReadableStream` 自行实现 SSE（如 `@microsoft/fetch-event-source`）。
2. **频道必须服务端决定**：按 `tenant_id` + `user_id` 订阅，**不接受前端传频道名**。
3. **不要在同一端同时接 SSE 与 WebSocket**，否则重连、去重、状态同步会有两套逻辑。

### 消息契约

只推"变更信号"，不推业务数据：

```json
{
  "type": "booking.updated",
  "entity_id": 123,
  "version": 5,
  "ts": "2026-11-21T10:00:00+08:00"
}
```

前端收到后按 `type + entity_id` 拉取详情。理由：

- 权限判断集中在 HTTP 接口，不在推送通道重复实现；
- 断线重连后可用 HTTP 补齐，不依赖消息完整性；
- 推送体积小，避免大对象与租户数据泄漏风险。

### 鉴权与连接管理

| 项 | 要求 |
|---|---|
| 握手 | 校验 JWT + 租户；失败立即断开 |
| 心跳 | WebSocket 30s ping/pong；SSE 用注释行保活 |
| 重连 | 指数退避，服务端按 `Last-Event-ID` 补发（SSE） |
| 多端 | 同一用户多设备连接需允许，但按连接计数限流 |
| 关闭 | 登出、令牌过期、租户停用需主动断开 |

## 7. 迁移路径

| 阶段 | 动作 | 风险 |
|---|---|---|
| 0 | 排期/预约展示状态改为纯派生（A），删除对应扫描逻辑 | 低，`display_status` 已是范例 |
| 1 | 建 `job_queue` 表 + worker，先迁"到期提醒"这类低风险任务（C） | 低，仅通知 |
| 2 | 迁会员卡激活/过期/解冻/作废（C + A 兜底） | 中，涉及状态机 |
| 3 | 课程完成、人数不足取消改为延迟任务（B） | 中，涉及扣次与退款 |
| 4 | 管理端接 SSE，小程序接 WebSocket | 低 |
| 5 | APScheduler 降级为每日对账，不再承担主路径 | 低 |

**迁移期最大风险是双执行**：新旧两套同时生效。规避方式：

- 每个任务有 `idempotency_key`（`type + entity_id + 目标状态`）；
- 按 `type` 开关灰度，迁完一类关一类；
- 对比期同时记录"新任务执行"与"旧扫描结果"日志，确认一致后再关旧逻辑。

## 8. 测试与验收

| 层 | 用例 |
|---|---|
| 单测 | 状态派生函数（时间边界：正好等于 `now()`、跨时区）；幂等键生成；重试与死信判定 |
| 集成 | 并发抢任务（多 worker 不重复）；任务失败后重试；租户隔离（A 租户任务读不到 B 租户数据） |
| 场景 | 部署重启期间到点事件仍被补执行；推送断线重连后能补齐状态 |
| 验收 | 关闭 APScheduler 后，卡状态/排期状态仍正确；同一任务执行 3 次只有 1 次副作用 |

## 9. 风险与 UNKNOWN

| 类型 | 内容 | 处理 |
|---|---|---|
| 风险 | 双执行导致重复扣次/重复退款 | 幂等键 + 灰度 + 对账 |
| 风险 | 时区混用（调度器 UTC，业务 Asia/Shanghai） | 统一以 DB `timestamptz` 为准，派生函数只比较绝对时间 |
| 风险 | 延迟队列积压 | 监控 pending 数量与最老任务延迟，设告警 |
| 风险 | SSE 被 Nginx 缓冲 | `proxy_buffering off`、`X-Accel-Buffering: no` |
| UNKNOWN | 小程序 WebSocket 域名与证书要求 | 需在微信后台配置 `socket` 合法域名 |
| UNKNOWN | 现有 8 个 job 之间的隐含顺序依赖 | 迁移前逐个梳理，必要时合并为一个编排任务 |
