## B. Python / FastAPI 深度题库（第一批）

说明：每道题包含：考察点、标准答案、项目结合、底层原理、生产实践、常见错误答案、面试官追问、优秀回答。


### Q1：为什么在本项目选择 FastAPI？如果约课接口存在高并发，你的异步模型是如何工作的？

【考察点】
- 框架选择理由、ASGI/asyncio 模型、Uvicorn、IO 并发优势、局限

【标准答案】
- 选 FastAPI 因为：高性能（基于 Starlette/asgi）、类型提示驱动的校验与文档、开箱即用依赖注入；搭配 Uvicorn 能提供高并发 IO 性能。项目约课场景大量 IO（DB、Redis、外部服务、LLM），async model 可以通过单进程多协程处理大量并发请求，减少线程上下文切换开销。

【项目结合】
- 约课流程涉及：鉴权（Redis）、库存检查（Postgres）、Agent 调用（HTTP/Tool）、通知（第三方）。这些都是网络 IO，使用 async 能显著提高吞吐。实际项目需把阻塞调用（比如同步 SDK、CPU 密集任务）隔离到线程池或后台任务。

【底层原理】
- async/await 基于事件循环（event loop），协程在遇到 await 时让出执行权；单线程内可切换大量协程；Uvicorn 提供事件循环与 socket 接入，Starlette 提供路由与中间件。

【生产实践】
- 确保所有 IO 客户端均为异步（asyncpg、httpx.AsyncClient、aioredis）；对同步库使用 run_in_executor；对 CPU 密集任务使用任务队列（Celery / RQ）或独立 worker。

【常见错误答案】
- 认为只写 async def 就一定异步高效；未限制并发导致数据库连接池耗尽；在协程内调用阻塞库没有处理。

【面试官追问】
1. 如果 async def 中执行阻塞代码会怎样？
2. 如何在 FastAPI 中安全地使用对象生命周期（例如 DB session）？
3. 怎样监控事件循环是否被阻塞？
4. 如果用了 sync 第三方 SDK，具体怎么改造？

【优秀回答】
- FastAPI 适用于 IO 密集型的约课场景。关键点是保证端到端异步：使用 asyncpg/aioredis/httpx.async；任何阻塞点（如第三方 SDK）放到 threadpool 或异步 wrapper；对 CPU 密集任务用后台 worker。同时设置合理的 DB 连接池并发上限与请求限流，防止连接池耗尽。监控使用 event loop lag、Apm traces 与指标（latency、connections）来发现问题。


### Q2：ASGI 与 WSGI 有何区别？为什么选 ASGI？

【考察点】
- 协议差异、异步支持、WebSocket、长期连接

【标准答案】
- WSGI 是同步接口，处理模型为一个请求占用一个线程；ASGI 是异步接口，支持协程、WebSocket、HTTP/2、长连接，更适合现代异步场景。FastAPI 基于 ASGI，支持高并发非阻塞 IO。

【项目结合】
- Agent 需要 WebSocket 或长连接能力（实时通知、流式 LLM），ASGI 提供这些能力。在高并发约课场景，ASGI 在资源效率上更好。

【底层原理】
- ASGI 抽象为生命周期事件与协程，事件循环切换、协程调度是核心；WSGI 只支持同步调用链。

【生产实践】
- 使用 Uvicorn/Hypercorn 做 ASGI server；确保中间件与依赖支持异步。

【面试官追问】
1. ASGI 下 middleware 与 WSGI 中有何不同？
2. 如何检测某个依赖是否支持异步？

【优秀回答】
- 选择 ASGI 是因为项目需要高并发网络 IO 与 WebSocket；确保依赖 async 化并监测 event loop 阻塞，即可保证稳定性。


### Q3：FastAPI 的依赖注入（Depends）什么时候会成为性能瓶颈？如何优化？

【考察点】
- 依赖作用域、亿量请求下的开销、缓存依赖、对象重建成本

【标准答案】
- Depends 在每次请求会根据依赖声明创建/注入对象；若依赖做了昂贵操作（如打开 DB 连接、读取大量配置）会成为瓶颈。优化方法：把昂贵的初始化上移到应用生命周期（startup event），对幂等轻量依赖用 lru_cache 或单例模式，合理设置依赖为同步或异步，并在路由上缩小依赖范围。

【项目结合】
- DB session 通过依赖注入提供，但不要在 Depends 中每次都创建底层连接池（连接池在 engine 层）。Agent 客户端/LLM 客户端应在 lifespan 初始化。

【底层原理】
- FastAPI 在解析请求处理前构建依赖树并逐层调用，复杂依赖树会带来 CPU 与内存成本。

【生产实践】
- 把不可变配置放到 app.state 或单例；只在生命周期事件中建立外部连接；使用轻量依赖作为局部适配器。

【面试官追问】
1. DB session 依赖到底应如何实现（同步 vs 异步）？
2. lifespan event 的实现细节？

【优秀回答】
- 将重资源（DB pool、http clients）在 startup 建好并放 app.state；在 Depends 返回短生命周期的 session（例如 AsyncSession 绑定到 request），并确保及时关闭，减少重复初始化。


### Q4：AsyncSession 为什么不能跨请求共享？如何管理请求级的 AsyncSession？

【考察点】
- 事务边界、会话状态、并发与线程安全

【标准答案】
- AsyncSession 不是线程安全且通常绑定到具体事务上下文，跨请求共享会导致事务混乱、脏数据。正确方式是为每个请求创建一个新的 AsyncSession 实例（工厂由全局 Engine 提供），在请求结束时 commit/rollback 并 close。

【项目结合】
- 在项目中通过 FastAPI 依赖生成 request-scoped AsyncSession：依赖中 await session.begin() 或使用 context manager，结束时确保 rollback on exception 并 close。

【底层原理】
- Session 持有单位工作集（identity map），并追踪实体状态。跨请求共享会导致状态污染和并发访问冲突。

【生产实践】
- 使用中间件或 Depends 提供 session，明确 commit/rollback，必要时设置短连接超时并监控连接泄漏。

【面试官追问】
1. 为什么不能把 Session 存到 global contextvar？（追问会引导到 request-scoped contextvar 可行性讨论）
2. 如何检测 session 泄漏？

【优秀回答】
- 每个请求使用独立 AsyncSession，借助 context manager/Depends 确保关闭。连接池大小与请求并发应匹配，监控未关闭 session 的日志/连接数异常来发现泄漏。


### Q5：数据库连接池耗尽会带来哪些后果？如何监控与应对？

【考察点】
- 连接池耗尽表现、超时、队列、backpressure、恢复策略

【标准答案】
- 后果：新请求等待连接或抛出超时/连接错误，导致 500/502；事件循环可能被阻塞，系统变慢。监控：连接池使用率、等待队列长度、连接创建/释放速率、数据库端活动（pg_stat_activity）。应对：限流、熔断、合理设置池大小、使用 queueing with timeout、在前端做请求削峰、异步退避重试、将长事务拆分。

【项目结合】
- 约课高并发场景应把 DB 连接池设为小于或等于 Postgres 可承受的并发连接数，使用中间件进行请求排队与限流；推荐把外部耗时操作（通知、LLM）移出主事务。

【底层原理】
- 连接池分配有限连接；请求阻塞等待导致协程等待 DB，若等待占用 event loop 资源会影响其他协程运行。

【生产实践】
- 为不同类型的工作设置不同连接池（普通查询 vs 写操作），使用读写分离降低主库压力；部署 connection pool metrics 到监控系统（Prometheus）。

【面试官追问】
1. 如何为每个服务实例计算合适的连接池大小？
2. 如果 Postgres max_connections 已用完怎么办？

【优秀回答】
- 根据 Postgres 最大连接数、实例数量与其他服务连接需求，倒推单实例 pool_size；同时在应用层实施限流和后端排队，避免瞬时洪峰击穿 DB。


### Q6：解释 commit、rollback、flush、refresh 的区别，以及何时需要显式 flush？

【考察点】
- 事务操作语义、flush 的触发时机、脏写风险

【标准答案】
- commit：提交事务到数据库，使更改持久化并释放锁；
- rollback：回滚事务，撤销未提交的更改；
- flush：把 ORM 的挂起更改写入数据库但不提交事务（执行 SQL），保证 DB 与 ORM 状态一致；
- refresh：从数据库重新加载实体状态到当前 session。

显式 flush 常用于在同一事务内需要在数据库层面读取刚写入的数据（例如依赖自增主键或触发器结果），或者在复杂并发逻辑中预先验证约束。

【项目结合】
- 在预约流程中：先插入 booking 并 flush 以获取 booking.id，然后调用外部通知 API；若通知失败可 rollback。

【底层原理】
- flush 将 ORM 的 pending changes 转换为 INSERT/UPDATE SQL；commit 在 flush 后提交事务并释放锁。

【生产实践】
- 避免不必要的 flush，减少数据库交互次数；对必须 flush 的场景控制在短事务内完成。

【面试官追问】
1. flush 会不会释放锁？（否，释放在 commit）
2. 在异步 Session 中 flush 的实现差异？

【优秀回答】
- flush 用于保证 DB 可见性但不提交事务。只在确实需要读取 DB 生成值或触发器结果时才用，否则会增加 IO 与锁持有时间。


### Q7：什么是 N+1 问题？selectinload 与 joinedload 如何缓解？在约课场景哪些查询易受影响？

【考察点】
- ORM 查询模式、关联加载策略、性能优化

【标准答案】
- N+1：为每个主实体额外发起一次关联查询，导致大量 SQL。selectinload 使用 IN (...) 批量拉取关联（两次查询），适合一对多、减少数据重复；joinedload 使用 JOIN 在一条查询中拉取，适合一对一或小数据量；两者权衡：joinedload 会导致数据重复与更大返回集。

【项目结合】
- 查询课程列表并展示教师信息与可用时段时容易触发 N+1。应在 repository 使用 selectinload(Teacher) 预取教师和 schedule 数据。

【底层原理】
- ORM 默认延迟加载会在访问关联属性时触发查询。selectinload 通过 IN 子句批量获取，joinedload 通过 JOIN 一次获取。

【生产实践】
- 使用 profiling（sqlalchemy echo 或 tracing）发现 N+1，选择合适的 load strategy，并在分页时注意 joinedload 导致行重复。

【面试官追问】
1. selectinload 对大量主表结果会怎样？
2. joinedload 在何种场景下更好？

【优秀回答】
- 对批量主实体推荐 selectinload；如果关联表很小或一对一场景可选 joinedload；关键是用 EXPLAIN/trace 验证并衡量网络与解析成本。


### Q8：约课接口同时有同步与异步调用方（小程序、管理后台、Agent），如何设计 API 并保证幂等与一致性？

【考察点】
- 幂等设计（idempotency key）、幂等 token、事务边界、重复请求处理

【标准答案】
- 对写操作（booking）提供幂等 key（客户端生成的请求 ID 或幂等 header），在服务端以唯一索引记录请求 ID 与结果，若重复请求直接返回上次结果。事务内需保证先写幂等记录再做业务操作，或在唯一约束冲突时做冲突处理（RETURNING）。

【项目结合】
- Agent 可能会由于网络问题重试 book_course；需要幂等 key 防止重复扣卡或重复占位。实现方式：bookings 表加上 request_id 唯一索引，插入冲突时返回已存在行。

【底层原理】
- 利用数据库唯一约束实现原子性（INSERT ... ON CONFLICT DO NOTHING/UPDATE）；或用分布式事务/乐观锁配合幂等记录表。

【生产实践】
- 对外接口要求传 idempotency_key；在后端统一接收并校验，设置合理 TTL，监控冲突率。

【面试官追问】
1. 如果使用唯一约束，如何返回已存在记录给客户端？
2. 幂等 key 放在哪存储更合适？

【优秀回答】
- 使用 request_id 唯一索引并用 INSERT ... ON CONFLICT DO UPDATE RETURNING，保证原子性并返回结果；同时在 audit 表记录调用链以便追溯。


### Q9：如何在 FastAPI 中实现请求级别的超时控制与取消？

【考察点】
- 请求超时、协程取消、cleanup、外部调用中断

【标准答案】
- 可在 Uvicorn 之上使用代理（NGINX）进行超时（proxy_read_timeout），并在应用层对长耗时操作使用 asyncio.wait_for 或在依赖中实现 timeout context。协程被取消后要处理 CancelledError 做清理（释放 session、解锁 Redis 锁）。外部 HTTP 客户端也需要传入超时并支持取消。

【项目结合】
- 约课操作若超过 3s 应回退并告知用户，请在主事务外排队处理或返回 202 并异步完成。确保取消能释放预占锁。

【底层原理】
- asyncio cancellation 会在 await 点抛 CancelledError，需捕获并执行 finally 清理。

【生产实践】
- 在关键操作加 timeout，使用后台任务或消息队列处理长任务，并监控 cancelled 指标。

【面试官追问】
1. asyncio.wait_for 与 signal.alarm 哪个更合适？
2. 如果任务被 cancel，但 DB 事务未 rollback，怎么办？

【优秀回答】
- 使用 asyncio.wait_for 在应用层控制超时，捕获 CancelledError 保证 rollback/释放资源。对于更长流程用异步后台任务并返回 202。


### Q10：如何对 FastAPI 服务进行压测（以约课场景为例），压测指标与瓶颈判断方法？

【考察点】
- 压测工具、指标、瓶颈定位（CPU/IO/DB/Redis/网络）

【标准答案】
- 使用 k6/locust/vegeta 进行压测；指标包括吞吐（RPS）、P50/P95/P99 延迟、错误率、连接数、DB 活动、event loop lag。瓶颈判断：若 CPU 饱和看系统负载、若 event loop lag 大表示阻塞、若 DB connections 高且慢查询多看 SQL；若 Redis 命令延迟升高检查慢命令或主从复制。

【项目结合】
- 针对单课程剩余1个名额场景做压力注入，关注 booking success rate 与冲突率，观察 DB 锁等待与事务时间分布。

【底层原理】
- 压测产生大量并发请求，导致资源竞争。要通过 metrics/trace 定位热点。

【生产实践】
- 在预生产环境逐步放大并发，结合 APM、pg_stat_activity、redis info、prometheus 指标分析瓶颈并优化。

【面试官追问】
1. 如何模拟真实用户行为（think time、重试）？
2. 压测发现 502、大量 500 如何排查？

【优秀回答】

### Q20：如何在本项目中处理第三方 API 调用失败（退避重试、熔断、补偿）？

【底层原理】

【生产实践】

### Q21：SQLAlchemy AsyncSession 的最佳实践：生命周期、事务边界与错误处理

【考察点】
- Session 生命周期、上下文管理、异常时的 rollback/close

【标准答案】
- 每请求使用独立 AsyncSession，通过依赖或 middleware 创建并在 finally 中确保 rollback on exception 并 close。事务边界应尽量小，把 I/O 密集或外部调用移出事务。错误时记录并上报，但不要吞掉异常以免掩盖失败。

【项目结合】
- 在 booking API 中，事务只包含检查库存与写 booking，通知放到后台任务，避免长事务占用连接。

【底层原理】
- Session 持有 identity map，事务与连接绑定，长事务占用锁与连接资源。

【生产实践】
- 使用 contextmanager pattern：
```
async with AsyncSession(engine) as session:
    async with session.begin():
        ...
```
并在应用层防止 session 泄漏。

【面试官追问】
1. 如果在 finally 中 close 抛异常怎么办？
2. session.begin vs begin_nested 区别？

【优秀回答】
- 捕获 close 抛出并记录；nested transaction 用于 SAVEPOINT 场景，例如在复杂逻辑中局部回滚。


### Q22：数据库事务隔离级别（READ COMMITTED、REPEATABLE READ、SERIALIZABLE）在约课场景的选择与影响

【考察点】
- MVCC、幻读、写偏差、性能与锁

【标准答案】
- READ COMMITTED 是默认，适合多数场景；SERIALIZABLE 提供最强一致性但会增加冲突与回滚概率。为保证库存正确性，可在写操作使用 SELECT FOR UPDATE 在事务内锁定行，而不必使用 SERIALIZABLE 全局隔离。

【项目结合】
- 对于单课程名额竞争，使用 SELECT FOR UPDATE 锁定课程库存行并在事务内检查与扣减，能保证单节点正确性且性能优于 SERIALIZABLE。

【底层原理】
- PostgreSQL 基于 MVCC，不同隔离级别通过快照与冲突检测实现一致性。

【生产实践】
- 在高并发下优先用行级锁与短事务，避免 SERIALIZABLE 造成频繁回滚。

【面试官追问】
1. SERIALIZABLE 回滚如何检测并重试？
2. 使用 FOR UPDATE 会影响读性能吗？

【优秀回答】
- 捕获 SerializationFailure 异常并退避重试；FOR UPDATE 只锁定行，不影响读取未锁行的快照查询。


### Q23：SELECT FOR UPDATE 如何工作？在多节点部署时有哪些限制？

【考察点】
- 行级锁、锁等待、死锁、分布式一致性

【标准答案】
- SELECT ... FOR UPDATE 在事务内对返回行加排他锁，阻止其他事务更新这些行。锁存在于单个数据库实例上，跨节点（读写分离、复制延迟）需注意主从读的问题；读从库由于延迟不能用于加锁操作，必须写到主库。

【项目结合】
- 在 booking 中对 course_row FOR UPDATE，检查剩余并减库存，确保单点正确。若使用多个 DB 实例，需要把写路由到主库。

【底层原理】
- PostgreSQL 使用 heavyweight lock 机制，锁持有直到事务结束。

【生产实践】
- 保持事务短小、设置 lock_timeout、监控 lock wait 和 deadlocks（pg_locks, pg_stat_activity）。

【面试官追问】
1. SELECT FOR UPDATE SKIP LOCKED 有什么用？
2. SKIP LOCKED 在公平性上有什么问题？

【优秀回答】
- SKIP LOCKED 适用于消费队列场景，能跳过被锁定记录以避免阻塞；但可能导致请求不公平或 starvation，需要按业务权衡。


### Q24：乐观锁（version 列）与悲观锁（SELECT FOR UPDATE）如何选择？

【考察点】
- 并发冲突概率、回滚成本、实现复杂度

【标准答案】
- 乐观锁适合冲突少的场景：在更新时比较版本号，若冲突则重试；悲观锁适合高冲突、必须确保顺序的场景。约课高争抢通常使用悲观锁（行锁），或结合幂等与快速失败的乐观锁策略。

【项目结合】
- 对热门课程使用悲观锁以减少冲突重试；对于非热点更新使用乐观锁降低锁争用。

【底层原理】
- 乐观锁不加锁，依赖版本校验；悲观锁在 DB 层加排他锁。

【生产实践】
- 根据冲突率监控选择策略，并实现指数退避重试与限流。

【面试官追问】
1. 乐观锁如何保证幂等？
2. 乐观锁频繁失败怎么优化？

【优秀回答】
- 合并幂等 key、在冲突高峰期切换到悲观锁或引入排队层降低冲突。


### Q25：唯一约束能否替代锁？如何用唯一约束实现幂等性？

【考察点】
- 原子性、约束冲突处理、ON CONFLICT

【标准答案】
- 唯一约束可用于幂等性（例如 request_id），通过 INSERT ... ON CONFLICT DO NOTHING/UPDATE 实现原子性。这适合幂等请求，但对库存减扣等复杂事务通常需要锁或原子更新语句（UPDATE ... WHERE available > 0 RETURNING）。

【项目结合】
- booking 表加 request_id 唯一索引，重复请求直接返回已存在记录。库存扣减用 UPDATE ... WHERE available > 0 RETURNING，以避免先读后写竞争。

【底层原理】
- 唯一约束由索引维护，违反约束会触发错误，可用 ON CONFLICT 语义处理。

【生产实践】
- 使用索引做好退避；监控 conflict 频率并排查客户端重复请求。

【面试官追问】
1. ON CONFLICT 哪些场景下不适用？
2. 如何避免表膨胀导致索引变慢？

【优秀回答】
- ON CONFLICT 适合幂等请求，复杂库存逻辑用原子 UPDATE 或行锁；保持索引健康并定期维护。


### Q26：如何设计 bookings 表的索引以满足查询：tenant_id, student_id 按 created_at DESC 分页？

【考察点】
- 联合索引、排序列、覆盖索引、分页性能

【标准答案】
- 建议使用联合索引：CREATE INDEX ON bookings (tenant_id, student_id, created_at DESC) 或者把 created_at 放在最后以支持 WHERE tenant_id=? AND student_id=? ORDER BY created_at DESC LIMIT 20。若返回列少可用 INCLUDE 来覆盖索引。

【项目结合】
- 为 tenant-scoped 查询加索引并考虑分区（按 tenant_id 或时间）以控制单表大小。

【底层原理】
- 联合索引能利用最左前缀原则，顺序影响能否使用索引排序而避免额外排序操作。

【生产实践】
- 使用 EXPLAIN ANALYZE 验证索引使用；考虑分区、materialized views 或 time-series 优化。

【面试官追问】
1. 为什么 created_at 放最后？
2. OFFSET 分页的缺点是什么？

【优秀回答】
- created_at 放最后以便 WHERE 过滤字段先命中索引；OFFSET 在大偏移下性能差，建议使用 cursor pagination（基于 created_at+id）。


### Q27：OFFSET 分页与 Cursor 分页（Keyset）区别？何时使用？

【考察点】
- 性能、稳定性、实现复杂度

【标准答案】
- OFFSET 在大页数时会跳过大量行并变慢；Cursor（keyset）以 last_seen_key 查询下一页，性能稳定且避免重复/漏行（在数据频繁写入时）。对用户活动流或 booking 历史建议使用 cursor pagination。

【项目结合】
- 学员查看历史预约应使用 cursor based pagination，client 传 last_created_at+id 作为 cursor。

【底层原理】
- OFFSET 需要扫描并丢弃前 N 行，keyset 用索引直接定位范围。

【生产实践】
- 设计 cursor 结构并支持兼容回退策略。

【面试官追问】
1. cursor pagination 的实现细节如何保证 stable ordering？
2. 如何处理数据删除导致 cursor 失效？

【优秀回答】
- 使用 created_at+id 做复合 cursor 保证唯一性；若 cursor 失效返回空或引导用户回到第一页。


### Q28：EXPLAIN ANALYZE 报慢查询如何定位？常见优化手段是什么？

【考察点】
- 查询计划分析、索引缺失、顺序扫描、排序、聚合开销

【标准答案】
- 使用 EXPLAIN ANALYZE 获取实际执行时间与节点信息；查看是否使用索引、是否出现顺序扫描、排序或 HashAggregate。优化：增加合适索引、重写查询、添加 WHERE 限制、避免 select *, 使用 materialized view 或增加 maintenance（VACUUM/ANALYZE）。

【项目结合】
- 对于课程列表过滤与统计查询，可能需要建立部分索引或 precompute 聚合数据。

【底层原理】
- Planner 基于统计信息选择执行计划，错误的统计会导致次优计划。

【生产实践】
- 定期运行 ANALYZE，保持统计信息准确；对大型表考虑分区并监控 planner choices。

【面试官追问】
1. 为什么 planner 选择顺序扫描而不是索引？
2. 如何更新统计信息？

【优秀回答】
- Planner 根据估算成本选择顺序扫描（当比例大时成本更低）；使用 ANALYZE 更新统计并考虑调整 planner settings 或添加 partial index。


### Q29：PostgreSQL 的 MVCC 如何工作？对约课高并发会有什么影响？

【考察点】
- 多版本并发控制、事务可见性、事务冲突与 VACUUM

【标准答案】
- MVCC 通过生成新版本（tuple）实现并发读写，读取使用快照看到合适版本，写会保留旧版本直到 VACUUM 清理。高并发写会产生大量 dead tuples，需要适当 autovacuum 调整，长事务会阻止 VACUUM 清理并影响性能。

【项目结合】
- booking 高频写入时监控 dead_tuples 与 autovacuum 累积，避免表膨胀与 bloat。

【底层原理】
- 每个 tuple 带 xmin/xmax，版本可见性通过事务 id 判定。

【生产实践】
- 调整 autovacuum thresholds、使用 shorter transactions、定期重建索引或 VACUUM FULL（需注意锁）处理 bloat。

【面试官追问】
1. long-running transaction 对 VACUUM 的影响？
2. 如何检测 table bloat？

【优秀回答】
- long txn 会保留旧版本阻止回收；用 pg_stat_user_tables 和 pgstattuple 检查 bloat，并计划维护窗口。


### Q30：如何检测与分析死锁？如何应对？

【考察点】
- pg_locks/pg_stat_activity、死锁样例、重试机制

【标准答案】
- 使用 PostgreSQL 日志（deadlock detected）与查询 pg_locks/pg_stat_activity 获取等待图。应对：缩短事务、确保锁顺序一致、在应用捕获死锁异常并重试带退避。

【项目结合】
- 约课中若多个事务交叉锁定用户与课程行，可能触发死锁。设计统一加锁顺序或使用单行锁降低概率。

【底层原理】
- 死锁发生在循环等待资源，Postgres 检测并中止一个事务。

【生产实践】
- 捕获 serialization/detect deadlock exceptions 并重试，记录锁等待链以分析根因。


### Q31：如何使用 partial index、GIN、BRIN 在业务表优化？

【考察点】
- 索引类型适配场景、jsonb 与全文、时间序列表优化

【标准答案】
- partial index 用于过滤高选择性条件（例如 active=true）；GIN 适合 jsonb、array、全文搜索；BRIN 适合大表按顺序列（时间）查询以减少索引大小。

【项目结合】
- 对于只查询 active bookings 可建 partial index；课程标签搜索可用 GIN(jsonb) 或 tsvector。

【底层原理】
- 不同索引类型在空间与查询成本上权衡，选择基于访问模式。

【生产实践】
- 用 EXPLAIN 验证并监控 index size，避免过多索引影响写性能。


### Q32：批量写入（bulk insert）到 bookings 的最佳实践？如何避免阻塞与 bloat？

【考察点】
- COPY、批量 INSERT、事务大小、索引维护

【标准答案】
- 使用 COPY 或批量 INSERT 分批提交（例如 1000 行/批），在大批量加载前可临时禁用部分索引或使用 unlogged table 再 swap。避免单个事务太大导致长时间锁与大量 dead tuples。

【项目结合】
- 导入历史 bookings 或批量生成课程排期时使用 COPY，随后 ANALYZE。

【底层原理】
- 大事务会占用 WAL 与锁资源并导致长事务问题。

【生产实践】
- 控制 batch size，监控 WAL 生成，使用 pg_repack 或 periodic vacuum。


### Q33：Alembic autogenerate 常见陷阱与 env.py 配置注意事项

【考察点】

【底层原理】

【生产实践】

### Q34：如何在高并发场景下设计库存减扣的原子 SQL（避免先读后写竞争）？

【考察点】
- 原子更新、RETURNING、条件更新

【标准答案】
- 使用单条原子 SQL：
```
UPDATE courses SET available = available - 1
WHERE id = :id AND available > 0
RETURNING available;
```
若返回行为空表示失败。这避免了先读后写的时间窗口。

【项目结合】
- 在 booking 事务中优先执行该 UPDATE 并检查 RETURNING，再写 booking 表。

【底层原理】
- WHERE 子句与 UPDATE 在单个语句内完成，保证原子性。

【生产实践】
- 结合唯一约束与幂等 key，避免重复扣减。


### Q35：如何使用 PostgreSQL 的 advisory locks 实现分布式锁？与 Redis 锁比较如何？

【考察点】
- advisory lock 语义、持久性、连接依赖、适用场景

【STANDARD ANSWER】
- Advisory locks 是数据库级别的应用锁，绑定于 session/connection，持有直到释放或连接关闭。适合需要事务内锁定且希望借助 DB 一致性的场景。与 Redis 锁比，advisory lock 依赖 DB 连接，不适合长时持有或跨服务崩溃处理，但优势是与事务同生命周期。

【项目结合】
- 对于需要强一致且在事务内完成的锁（如按课程 id 排队）可使用 advisory lock；跨进程/跨语言协调则用 Redis 并配合 watchdog。

【底层原理】
- advisory lock 底层由 PostgreSQL 管理并在连接断开时自动释放。

【生产实践】
- 小心 connection leak，避免忘记释放 advisory lock 导致阻塞；对比 Redis，advisory lock 更简单一体化但不适合高频短锁跨服务场景。


### Q36：如何设计并监控 PostgreSQL 连接与资源（max_connections、work_mem、statement_timeout）？

【考察点】
- 参数影响、内存估算、连接共享方案

【标准答案】
- 根据机器内存估算最大并发连接：每连接大致消耗 base_memory + work_mem * active_workers。可以通过 PgBouncer 用连接池减少后端连接数。设置 statement_timeout 防止长查询，配置 work_mem 控制排序/聚合内存使用。

【项目结合】
- 在容器化部署中评估每实例连接需求并配置 pool_size，小实例使用 PgBouncer 共享真实 DB 连接。

【底层原理】
- 每连接分配一定内存，过多连接可能导致 OOM。

【生产实践】
- 监控 pg_stat_activity、connection usage、OOM events；使用 PgBouncer transaction pooling 提升吞吐。


### Q37：如何在 Postgres 中做审计（booking 操作的变更记录）？

【生产实践】

### Q38：如何设计 PostgreSQL 分区以支持海量 bookings（按 tenant 或按时间）？

### Q40：缓存与数据库的一致性策略（缓存失效、缓存穿透、灰度更新）

【考察点】
- Cache-aside、write-through、invalidate策略、TTL选择

【生产实践】
- 设计监控 cache hit/miss、穿透保护（bloom filter）、并在故障演练中验证一致性恢复流程。

## D. Redis 深度题库（Q41–Q60）

### Q41：为什么在本项目用 Redis 存 Agent 会话与上下文？Redis 与 PostgreSQL 的职责如何划分？

【考察点】
- 适用场景、数据特性、性能与持久性考虑

【标准答案】
- Redis 适合高频读写、低延迟、TTL 管理的会话型数据；Postgres 适合关系数据与强一致性事务。Agent 会话为短期上下文、频繁更新且可容忍部分丢失（可从 DB/日志恢复），因此放 Redis 可降低 DB 压力并提高性能。

【项目结合】
- Agent conversation history 存 Redis list/hash，关键业务事实（booking 成功、会员卡消费）写入 Postgres 作为 SOT。

【底层原理】
- Redis 是内存数据库，操作速度快但持久化策略与数据恢复语义与 RDB/AOF 相关；Postgres 提供 ACID 保证。

【生产实践】
- 对于关键事件做双写（Redis + Postgres 或使用 change capture），并设计恢复流程以防 Redis 数据丢失。

【面试官追问】
1. Redis 宕机后如何恢复会话？
2. 是否需要对会话做持久化备份？

【优秀回答】
- 关键业务结果持久化到 Postgres；对会话可定期 snapshot 或写入日志流以便重建。Redis 丢失不会影响 SOT。


### Q42：Redis 数据结构选择（String/Hash/List/Set/Sorted Set）在 Agent 场景如何使用？

【考察点】
- 数据结构语义、适配场景

【标准答案】
- String：简单键值或计数（例如 rate limit）；
- Hash：存储对象属性（conversation metadata）；
- List：聊天消息队列（append/read range）；
- Set：快速存在性检测与去重；
- Sorted Set：带 score 的时间序列或优先级队列（recent conversations by last_activity）。

【项目结合】
- conversation_id -> list of messages（List），conversation metadata 用 Hash 存储 TTL。

【底层原理】
- 各数据结构提供不同的时间/空间复杂度与原子操作。

【生产实践】
- 根据访问模式选结构并注意内存碎片化与最大键大小。

【面试官追问】
1. 为什么不把 messages 存 JSON String？
2. Redis List 与 Stream 的差异？

【优秀回答】
- List 支持快速 push/pop 与 range，Stream 适合消费组与持久流处理；当需要消费者组与持久化消费语义时选 Stream。


### Q43：Redis 分布式锁（基于 SETNX 或 RedLock）实现细节与风险

【考察点】
- 可靠性、时钟漂移、互斥语义、锁超时

【标准答案】
- 简单锁用 SET key value NX PX ttl 返回成功；释放时需用脚本核对 value 避免误删。RedLock 方案在多节点上更健壮但复杂，且在某些故障模型下仍有争议。关键风险：时钟漂移、网络分区导致锁错判、持久持有导致死锁。建议结合 TTL、watchdog、和后备策略。

【项目结合】
- 对热门课程抢占可用名额的临界段使用 Redis lock 短时保护，主写仍落库。

【底层原理】
- Redis 单实例提供原子 SET NX PX；分布式场景需考虑多副本选举。

【生产实践】
- 使用 lua 脚本释放锁，设置合理 ttl 并监控 lock hold time，避免长事务在持锁期间阻塞。

【面试官追问】
1. RedLock 是否真的安全？
2. 如果持锁过程中应用崩溃如何保证释放？

【优秀回答】
- RedLock 提供在多数节点达成的锁，但仍受网络分区影响；应设计为短锁并在 DB 层有最终一致性保障。


### Q44：如何用 Redis 实现高并发场景下的计数与限流？（令牌桶、漏桶、滑动窗口）

【考察点】
- 算法选择、原子性、性能

【标准答案】
- 令牌桶适合突发限流、漏桶适合平滑速率、滑动窗口更精确可用 lua 脚本实现原子性。在 Redis 使用 lua 保证原子更新并减少往返。

【项目结合】
- 对 booking API 实现 per-tenant、per-user 限流，防止恶意刷单。

【底层原理】
- Lua 在 Redis 内部执行保证原子性且效率高。

【生产实践】
- 监控限流触发率并支持动态调整配额。

【面试官追问】
1. 如何实现全局分布式限流？
2. 滑动窗口和 fixed window 的 trade-off？

【优秀回答】
- 全局可用 consistent hashing 或集中限流服务；滑动窗口更平滑但实现复杂，fixed window 简单但会在边界产生突发。


### Q45：Redis Lua 脚本的使用场景、性能与陷阱

【考察点】

## E. 高并发 / 分布式（约课场景）深度题库（Q51–Q80）

### Q51：单课程剩余 1 个名额，100 个并发请求如何保证只有 1 个成功？总体策略有哪些？

【考察点】
- 原子更新、行锁、分布式锁、幂等、排队

【标准答案】
- 方案：
  1. 数据库原子更新：UPDATE courses SET available = available - 1 WHERE id=:id AND available > 0 RETURNING id; 成功则创建 booking。此方案在单 DB 主库上最简单可靠。
  2. 悲观锁：在事务内 SELECT FOR UPDATE 锁定行后检查并扣减，确保串行更新。
  3. Redis 预扣减 + 异步落库：使用 Redis 原子递减并在后端消费队列逐条入库，需处理失败补偿与幂等。

【项目结合】
- 推荐优先使用数据库原子 UPDATE + 唯一约束校验，并在高并发时结合限流与排队。

【底层原理】
- DB 单语句原子性与索引维护保证并发下只有首个 UPDATE 成功返回行。

【生产实践】
- 对热点课程做限流、分批上报 metrics，使用 circuit breaker 与退避重试，监控冲突率与响应。对超高并发用排队/队列做前端削峰。

## G. API Client / Token 自动刷新（Q71–Q80）

### Q71：为什么把 API Client 抽成 packages/api-client？有哪些好处与陷阱？

【考察点】
- 共享逻辑、版本管理、跨端差异处理

【标准答案】
- 集中实现鉴权、token 刷新、tenant header 注入、错误处理和重试策略，避免每端重复实现并统一行为与兼容性。但需注意版本发布、API 兼容和多端差异（Web localStorage vs 小程序 storage）。

【项目结合】
- packages/api-client 提供 axios 拦截器，处理 401 自动刷新并注入 x-tenant-slug，保证管理后台与小程序一致性。

【生产实践】
- 使用 semantic versioning，提供 clear migration guide，并在 CI 校验各前端对 client 的兼容性。


### Q72：token 自动刷新的设计：单飞（single-flight）防止并发刷新怎么实现？

【考察点】
- 请求协调、锁、Promise/async handling

【标准答案】
- 在客户端维护一个刷新锁（promise）。当第一个请求触发刷新时，其他 401 请求等待该 promise 完成并复用新 token，避免并发多次刷新。实现注意边界条件：刷新失败要回退并使等待请求失败或跳转登录。

【项目结合】
- 在 API client 中实现 refreshInProgress promise；刷新成功 resolve 并重试挂起请求。

【生产实践】
- 监控 refresh 请求量与失败率，避免 refresh token 滥用导致安全风险。


### Q73：若同时 20 个请求都收到 401，如何在后端防止 token 刷新风暴引发问题？

【考察点】
- 后端限流、refresh token 单次使用、黑名单策略

【标准答案】
- 后端应限制 refresh token 的单次并发使用（例如一次 refresh 请求只接受一次 jti），并在服务端记录 refresh 请求频率，必要时短期封堵或要求 re-auth。客户端侧 single-flight 避免同时触发也很关键。

【生产实践】
- 在 Redis 中维护 refresh in-flight 标识与 TTL；监控异常停留并触发告警。


### Q74：refresh token 存储在小程序与 web 的区别，如何防止 XSS 与 token 泄露？

【考察点】
- 存储位置、安全性、跨平台策略

【标准答案】
- web: 避免 localStorage 存放长期敏感 token（XSS 风险），可用 HttpOnly cookie 或短期 access token + refresh token in secure storage；小程序：受限运行环境但仍需加密与最小权限存储。最小化 token 权限与过期时间并支持 token rotation。

【生产实践】
- 限制 token scope、使用 refresh rotation（旧 token 失效）、监控异常登录并支持强制登出。


### Q75：如何在 API Client 中实现透明重试与重放（幂等）策略？

【考察点】
- 幂等性、退避、幂等 key

【标准答案】
- 对幂等 GET/PUT 等自动重试，POST 等写操作需带 idempotency_key 才能安全重试。实现退避与抖动，最大重试次数并记录重试指标。

【生产实践】
- API client 在遇到网络错误重试，遇到 409/unique constraint 时不盲目重试。

## H. 多租户 / RBAC（Q76–Q90）

### Q76：为什么使用 tenant header（X-Tenant-ID / X-Tenant-Slug）而不是从 JWT 中直接读取？

【考察点】
- 灵活性、安全、代理场景

【标准答案】
- Header 提供前端可控制的租户上下文并支持多租户切换场景；但信任边界在后端，服务端必须校验 header 与用户权限一致，不能盲目信任前端传值。JWT 通常包含用户身份，后台需校验 header 与用户可访问租户权限。

【生产实践】
- Middleware 校验 header 与用户的租户列表，拒绝越权请求并记录审计。


### Q77：middleware 如何确保 repository 层始终带上 tenant filter？

【考察点】
- ContextVar、自动注入、编码约束

【标准答案】
- 使用 ContextVar 在 middleware 中设置当前 tenant，然后在 TenantAwareRepository 或 query injection 层自动加入 WHERE tenant_id = current_tenant。并在 CI/PR 审查检查不得手写 raw SQL 绕过 repo。

【生产实践】
- 单元测试与静态分析确保 repository 继承 TenantAwareRepository，并加入 runtime assertion。


### Q78：如何防止租户越权（IDOR）？举检测与修复办法

【考察点】
- 访问控制、校验、审计

【标准答案】
- 服务端在每个资源访问点校验 resource.tenant_id 是否与请求 tenant 相符；添加集成测试覆盖越权场景，并在审计日志中记录 access attempts。使用自动化安全扫描工具发现 IDOR。

【生产实践】
- 强制服务端校验并在 PR 审查中检测未加 tenant filter 的 repository 函数。


### Q79：RBAC 实现要点：权限模型与缓存策略

【考察点】
- 权限表达、缓存与失效

【标准答案】
- 角色-权限表设计、按角色缓存权限在 Redis，变更权限时失效并通知各实例刷新Cache。权限校验应在路由/handler 层做，并在服务端做最终确认。

【生产实践】
- 对权限变更做事件广播刷新缓存并记录变更历史。


### Q80：多租户的数据库隔离策略：共享 schema、单库多租户、单租户库的权衡

【考察点】
- 隔离等级、成本、运维复杂度

【标准答案】
- 共享 schema 低成本但需严格逻辑隔离；单库多租户（database per tenant）更强隔离但成本高；单租户库最高隔离但运维复杂。选择基于租户规模与合规需求。

【生产实践】
- 对大客户采用独立 DB，小客户共享 schema 并通过 tenant_id 强制隔离。

### Q118：场景：Redis CPU 100%，如何判断是 slow command 还是 hot key？

【考察点】

【标准答案】

### Q119：场景：Docker container 不断 restart，如何排查？

### Q120：场景：Nginx 502 Bad Gateway，如何定位？

【标准答案】
