## 三、一致性红线（出现任一即打回）

1. 把预约成功画成"签到成功/已核销"——违反"预约≠签到≠核销"模型
2. 出现后端不存在的 API 路径被画成可用功能且无"待开发"标注（吸取 membership.ts 虚构端点教训）
3. 学员端展示操作人、幂等键、内部错误堆栈等非业务字段
4. 未确认决策被画成确定交互且无占位标记
5. 原型展示 tenant_id / user_id 作为业务参数由前端传递的任何暗示（身份只走 Header/Token）

## 四、演示数据集要求（Figma 页面数据须贴近真实字段）

- 卡产品 ≥2 个：次卡（10 次/90 天/适用指定课程）+ 期限卡（30 天不限次）
- 学员卡覆盖 5 态：PENDING / ACTIVE（含 remaining=0 用尽样例）/ EXPIRED / FROZEN（含冲突样例）/ CANCELLED
- 排期：含满员排期 1 个、未来 7 天内排期 ≥3 个
- 预约：覆盖 BOOKED/CANCELLED/CHECKED_IN/COMPLETED 各 1；含"计划卡已作废但预约有效"1 条（演示 D3）
- 流水：ISSUE/CONSUME/RESTORE/EXPIRE 各 ≥1 条，booking_id 可关联

## 五、验收流程

1. Architect 按本清单逐项预检 → 出预检记录
2. 产品负责人确认 D1-D8 决策与原型占位处理一致性
3. 用户人工走查第六节演示脚本（或委托评审）
4. 通过后：本目录状态标记 READY_FOR_FIGMA，Execution Board 登记后续开发依赖（D3/D5/D7 涉及的后端任务进入 feature-backlog）

## 六、标准演示脚本（验收现场使用）

1. **A**：管理员发卡 → 学员小程序激活 → 选课选排期 → 选卡提交 → 结果页"已扣 1 次·剩余 N"
2. **B**：多卡学员在确认页切换两卡，余额预览联动 → 提交
3. **C**：我的预约取消 → 回补预览 → 确认 → 卡余额 +1；改期按钮展示 D7 占位
4. **D**：教师排期名单签到 → 完成；管理端 P-A6 同排期代签到 → 重复签到被拒
5. **E**：打开"计划卡已作废"的预约警示条 → 换卡出口（占位）+ 联系机构出口
6. **F**：卡列表展示用尽/过期/冻结/作废徽标 → 管理端作废时影响面提示（占位）
7. **G**：学员 P-M2 与管理端 P-A4 打开同一张卡：流水一致、字段口径符合最小化规则
