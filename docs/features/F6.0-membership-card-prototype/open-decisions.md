## D1 扣次时机：预约预扣 vs 签到扣（首次核销激活）

- **现状**：预约创建时同事务扣次（booking/service.py:130-155）；签到/完成只推进状态，不触碰卡；卡激活与核销完全解耦。
- **推荐方案：预约预扣 + 排期 COMPLETED 确认**（联动 D9 用户确认方案）。次卡预约时预扣（used\_credits+1），排期 COMPLETED 时确认不回补，排期 CANCELLED 时回补。期卡预约不扣次，首次排期 COMPLETED 时激活并起算有效期。签到/完成只推进 booking 状态，不再触碰卡。理由：事务一致性已被 F4.x 验证（幂等键+行锁+回补）；"正常上课"= 预约+排期 COMPLETED，不以签到为准。
- **备选方案：签到扣次 + 首次核销激活**。预约仅"预留"，签到时 CONSUME 并触发 PENDING→ACTIVE。影响：预约不再锁定课时（可超卖）、需要"预留额度"概念、取消/缺席语义重构、全部测试重写。
- **影响面**：流程 A/C/D 全部交互、对账口径、超卖风险、F5.1 AI 预约链路话术。**与 D9 联动**。

## D2 次卡"用尽"是否独立状态

- **现状**：无 EXHAUSTED 枚举；remaining=0 仍 ACTIVE（membership/models.py:49-57）。
- **推荐方案：不新增状态**，前端以余额徽标表达"已用尽"。理由：状态机加态要迁移 Check 约束（F4.4 刚落地）与 scheduler，收益仅是展示。
- **备选方案：新增 EXHAUSTED 态**。影响：DB 约束变更、过期/作废迁移矩阵、恢复次数（续卡）时的状态回转规则。
- **影响面**：P-M1/P-M2 卡状态展示、P-A2 管理列表筛选、D4 续卡规则。

## D3 计划课卡失效后的替代策略

- **现状**：预约后卡冻结/过期/作废，系统零处理；学员到店才发现。回补在卡被删除（FK SET NULL）后去向未定义。
- **推荐方案：提示 + 自助换卡 + 人工兜底三层**：a) 卡状态变更时预约列表警示；b) 学员可换卡改派（依赖 D7 原子化）；c) 无替代卡时引导联系机构。管理端作废/冻结前展示"该卡有 N 个有效预约"影响面。
- **备选方案：自动顺延**（预约自动切到同产品其他可用卡）。影响：需要排序策略、扣次/回补差值处理、用户知情权问题，复杂度高，不推荐首版做。
- **影响面**：流程 E/F 全部、P-M6/P-A2/P-A5、conflict-check 端点扩展（新增"受影响预约"查询）。

## D4 有效期起止边界

- **现状**：valid\_from/expire\_at 字段存在，scheduler 按 expire\_at\<now 判过期；但 expire\_at 当天能否预约/签到、PENDING 卡生效日前能否预约，产品层未定义。
- **推荐方案**：expire\_at 当天 23:59:59 前可预约可签到（含当天）；PENDING 卡（未到生效日）不可预约，选卡列表灰显"MM-DD 生效"。
- **备选**：过期即不可签到（更严格，易引发到店纠纷）。
- **影响面**：P-M3/P-M4 选卡过滤规则、P-T1 签到校验、scheduler 判定文案。

## D5 缺席（NO\_SHOW）处理

- **现状**：NO\_SHOW=5 仅存在于枚举与 Check 约束，无触发端点、无扣次规则、无补签。
- **推荐方案：自动消解（联动 D9）**。排期 COMPLETED 即扣，学员是否到场不影响扣次结果；NO\_SHOW 状态保留但不再有"扣不扣"的决策。教师/管理员仍可标记缺席（记录用途，不触发回补）。
- **备选**：缺席回补 N 次中 1 次 / 缺席扣双倍。影响：需要扣次规则表与对账说明。
- **影响面**：P-T1/P-A6 操作按钮简化、P-M6 学员端展示。**与 D9 联动**。

## D6 多卡默认推荐策略

- **现状**：小程序 getDefaultSelectedCard 有简单默认逻辑，策略未产品化。
- **推荐方案：先过期优先 → 其次剩余次数少优先 → 同分取先发放**。理由：最大化卡利用率，降低临期浪费，是行业惯例。
- **备选：让学员每次自选（无默认）/ 固定顺序**。影响：预约确认页多一步点击。
- **影响面**：P-M4 默认选中逻辑展示与说明文案。

## D7 改期与改派的原子性

> **已实现（F6.5，2026-10-22）**：`POST /api/v1/bookings/{booking_id}/reschedule`。
> - 改期 = 旧约 `CANCELLED` + 新约 `BOOKED` 同事务；纯改派 = 原地更新 `membership_card_id`
> - 锁序 `advisory(tenant,student)` → booking `FOR UPDATE` → schedule(id ASC) → card(id ASC)
> - 幂等：旧约状态 + `booking_reschedules` 审计表（部分唯一索引）+ 可选 `Idempotency-Key`
> - 次卡同卡「回补再扣」；期卡/无限卡 no-op；期卡有效期不由改期改写
> - 与 D-1~D-11 的完整口径见 `docs/features/F6.5-atomic-reschedule/requirement.md` §11

- **现状**：无 reschedule/改卡端点；改期=取消+重约，中间存在"已回补未锁定"窗口与两头落空风险。
- **推荐方案：新增原子改期端点**（同事务：回补原卡→锁定新排期→扣新卡/同卡），UI 上"确认改期"一次完成。**原子改派卡**（流程 E 出口1）复用同一事务骨架。
- **备选：维持两步**，UI 强提示中间态风险。影响：实现成本为零，但体验与一致性差。
- **影响面**：流程 C/E、P-M6/P-M7 交互、后端新端点（原型标注"待开发"）。

## D8 退款与撤销核销

- **现状**：TransactionType.REFUND/ADJUST 仅枚举占位；无退款流程、无撤销某笔核销的产品化端点；支付渠道未接（F6.1）。
- **推荐方案：本版原型只画入口占位**（管理端卡详情"申请退款"灰置 + "依赖 F6.1"标注）；撤销核销列为 F6.x 独立特性，不进本原型。
- **备选**：先做线下退款登记（不动支付，只写 REFUND 流水+状态留痕），管理端可用。影响：需定义审批流与对账口径。
- **影响面**：P-A4/P-M2 页面按钮、流程 F/G 终态。

## D9 期限卡预约校验：首次课程完成激活 + 预期有效期冲突预校验

> 背景：期限卡（period）`total_credits=None` 不扣次数（membership/service.py:1365-1366），仅按有效期计费。原预扣模式下三处漏洞（已用代码验证）：
>
> 1. `deduct_credit` 用 `now` 校验卡有效期，不校验排期上课时间（membership/service.py:1352-1363）→ 可用快过期卡预约未来课
> 2. `check_in_booking` 不读取/校验 membership\_card 状态（booking/service.py:287-297）→ 过期卡仍能签到
> 3. 期限卡重叠无次数代价，`allow_duplicate` 续卡可让两张期限卡同时 ACTIVE

- **现状**：学员可用 10-03 到期的卡一预约 10-10 的课（预约成功），到店签到时卡一已 EXPIRED 仍能签到成功，卡二（10-04 起）的权益被溢出消耗。
- **推荐方案：首次课程完成激活（PENDING→COMPLETED 驱动）+ 预期有效期冲突预校验**（用户确认方案，覆盖原"排期时间基准"与"补三处校验"方案）：

  **核心定义**："正常上课"= 预约成功 + 排期状态变为 COMPLETED，不以学员是否签到为准。学员预约了但没到场，只要课正常开了就算消费。

  **期卡规则**：
  1. 发卡时一律 PENDING，valid\_from / expire\_at 留空待定（不在发卡时算）
  2. 预约时不激活、不扣次；按"排期日 + validity\_days"计算**预期有效期**（valid\_from=排期日, expire\_at=排期日+validity\_days-1），仅用于冲突预校验，不写入卡
  3. 预约时做**区间重叠冲突检查**：该卡的预期有效期与学员已有同课程类型 ACTIVE/PENDING 卡的有效期（或预期有效期）做标准区间重叠判断（复用 scheduler.py:183-194 逻辑），有交集则拒绝预约
  4. 排期 COMPLETED 时：若卡仍 PENDING → 激活（status=ACTIVE），写入 valid\_from=排期日、expire\_at=排期日+validity\_days；若已 ACTIVE（非首次）→ 无操作
  5. 排期 CANCELLED 时：期卡不激活，PENDING 保持；次卡回补
  **次卡规则**：
  1. 预约时预扣（used\_credits += 1，产生 CONSUME 流水，与当前逻辑一致）
  2. 排期 COMPLETED 时：确认扣次（不回补，CONSUME 已记录，无需额外操作）
  3. 排期 CANCELLED 时：回补（used\_credits -= 1，产生 REFUND 流水，与当前取消逻辑一致）
  **缺席（D5 联动）**：自动消解——排期 COMPLETED 即扣，学员是否到场不影响扣次结果；NO\_SHOW 状态保留但不再有"扣不扣"的决策。

  **配套规则（必须同步实现）**：
  a. **PENDING 永不过期兜底**：scheduler 新增任务——PENDING 期卡发卡后 N 天（建议 90 天）无任何 COMPLETED 排期 → 自动 CANCELLED（"超期未激活"）
  b. **freeze 对 PENDING 拒绝**：service.py:627-632 的 freeze 方法新增 `if status == PENDING: raise "未激活卡不可冻结"`（valid\_from 未定，冻结无意义）
  c. **scheduler EXPIRED 任务扩展**：扫描条件从 `status == ACTIVE` 改为 `status IN (ACTIVE, PENDING)`，使过期 PENDING 卡（valid\_from 已定但 status 未流转的遗留卡）也能被标 EXPIRED；valid\_from 为空的 PENDING 卡走规则 a
  d. **冲突检查入口搬入预约**：create\_booking 或 deduct\_credit 内复用 scheduler.py:183-194 的区间重叠检查逻辑，传入预期有效期
- **备选方案 A：排期时间基准校验**（原推荐方案）。不改发卡逻辑，deduct\_credit 传 schedule\_time 替代 now，允许 PENDING 卡预约。缺点：PENDING 期卡的有效期从发卡日算，学员囤卡期间有效期在流逝，需补"最迟激活期限"等规则；且"预约即扣 vs 课程完成才算消费"语义不如推荐方案清晰。
- **备选方案 B：改签到扣次**。签到时刻=上课时刻，有效期校验自然对齐；但需配套预约轻量校验、缺席扣次、有效期起算点等决策，改动面大，不推荐首版采用。
- **效果对照**：
  | 场景                       | 结果                                                               |
  | ------------------------ | ---------------------------------------------------------------- |
  | 卡一约 10-05 的课             | 预期有效期 10-05\~10-07，无冲突→预约成功，排期 COMPLETED 后激活，valid\_from=10-05 ✅ |
  | 卡二约 10-06 的课（卡一已约 10-05） | 预期有效期 10-06\~10-08，与卡一 10-05\~10-07 有交集→冲突→拒绝 ✅                  |
  | 卡二约 10-08 的课（卡一已约 10-05） | 预期有效期 10-08\~10-10，与卡一 10-05\~10-07 无交集→允许 ✅                     |
  | 学员约了 10-05 的课但没签到        | 排期 COMPLETED → 期卡激活+扣次，学员自己亏 ✅                                   |
  | 学员买卡后 90 天未约课            | scheduler 自动 CANCELLED ✅                                         |
- **影响面**：P-M3/P-M4 选卡过滤（PENDING 可选+冲突校验）、P-T1/P-A6 排期完成触发激活、booking/service.py 排期完成钩子、membership/service.py 发卡/扣次/freeze、scheduler 新增 PENDING 超期取消任务+EXPIRED 扫描扩展、F5.1 AI 预约选卡逻辑。
- **联动决策**：D1 扣次时机→改为"预约预扣+排期COMPLETED确认"；D5 缺席→自动消解（课开即扣）；D4 有效期边界→期卡 valid\_from 从首次 COMPLETED 算。

## D10 预约跨排期时间段重叠校验（**已实现**）

> 登记日期：2026-10-19｜状态：**已实现（F6.4，2026-10-22）**｜详见 [D10 立项文档](./D10-booking-time-conflict-validation.md)、交付记录 `docs/features/F6.4-booking-time-overlap/`
> **性质**：真实后端缺口，非"待产品决策"的未确认项；已落地到 `BookingService.create_booking`（Service 层）。

- **现状**：真实后端 `apps/api/src/app/modules/booking/service.py::create_booking`（L51-93）**没有**「同一学员跨排期时间段重叠」校验——只校验了同排期重复预约（L87-89 `find_active_booking` + 部分唯一索引 `uq_bookings_schedule_student_active`）、容量（L70-71）、时间窗口（L75-85）。因此学员可同时约下两门时间重叠的课。
- **原型现状**：F6.0 原型此前只有「冲突」= 会员卡有效期重叠（`cardConflict`，D9），**不含**课程时间段重叠。本次已在 P-M3→P-M4 约课链路的确认阶段补「时间段重叠 → 拦截」演示态（演示数据：目标排期 S6 19:30-20:30 与已约排期 S1 19:00-20:30 重叠）。
- **推荐实现口径**（正式开发）：
  1. 在 `create_booking` 的同排期重复校验之后、扣次之前，新增跨排期时间段重叠校验；
  2. 取该学员**进行中**预约（status ∈ BOOKED / CHECKED_IN，排除 CANCELLED / COMPLETED）关联排期的 `start_at` / `end_at`（`schedule/models.py:42-43`）；
  3. 标准区间重叠判定：`a.start < b.end && b.start < a.end`（开闭区间口径，边界相接不算冲突）；
  4. 命中则抛 `BusinessException`（如"该时间段与您已约课程《XXX》冲突，无法预约"），与写操作同事务/同回滚语义；查询走 Repository（`TenantAwareRepository` 自动注入租户，禁止绕过）。
- **解耦说明**：该校验与「会员卡有效期重叠」（D9 `cardConflict`）**必须解耦**——前者按排期时间轴判定，后者按卡有效期区间判定；两者相互独立、互不覆盖，命中卡冲突时优先提示卡冲突。
- **影响面**：`booking/service.py` 新增校验 + Repository 查询；P-M4 确认阶段文案；F5.1 AI 预约链路话术；需补后端单测/集成测试（跨排期重叠拒绝、非重叠放行、跨租户隔离）。
- **备注**：原始需求已明确"正式开发需在 `create_booking` 增加跨排期时间段重叠校验"，本项无产品方案分歧，属确定性待开发项。
