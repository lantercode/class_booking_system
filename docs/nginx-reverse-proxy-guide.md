# Nginx 反向代理完整指南

## 一、什么是代理？

### 生活中的代理

```
你想买房
    ↓
找房产中介（代理人）
    ↓
中介帮你联系房东
    ↓
房东把房子给中介
    ↓
中介把房子交给你
```

**关键点**：
- 你不需要直接找房东
- 中介替你完成了"联系房东"这件事
- 中介可以帮你做额外的事（砍价、验房、办手续）

### 计算机网络中的代理

```
客户端（浏览器）
    ↓
代理服务器
    ↓
目标服务器
```

| 角色 | 生活中的对应 | 网络中的对应 |
|------|------------|------------|
| 你 | 想买房的人 | 浏览器/用户 |
| 中介 | 房产中介 | 代理服务器 |
| 房东 | 房子所有者 | 目标服务器 |

## 二、正向代理 vs 反向代理

### 正向代理

```
你的电脑（在中国）
    ↓
代理服务器（在美国）
    ↓
Google
```

**谁知道什么？**

| 角色 | 知道目标服务器吗？ | 知道真实客户端吗？ |
|------|------------------|------------------|
| 客户端（你） | ✅ 知道 | ✅ 知道 |
| 代理服务器 | ✅ 知道 | ✅ 知道 |
| 目标服务器（Google） | ❌ 不知道 | ❌ 不知道 |

**为什么叫"正向"？**
- 客户端**主动选择**使用代理
- 客户端**知道**代理的存在
- 客户端**配置**代理地址

**解决什么问题？**
- 翻墙
- 匿名访问
- 公司内网统一代理

---

### 反向代理

```
用户浏览器
    ↓
https://api.seplume.com
    ↓
Nginx（反向代理）
    ↓
FastAPI :8000
```

**谁知道什么？**

| 角色 | 知道后端服务器吗？ | 知道真实客户端吗？ |
|------|------------------|------------------|
| 客户端（用户） | ❌ 不知道 | ✅ 知道 |
| 反向代理（Nginx） | ✅ 知道 | ✅ 知道 |
| 后端服务器（FastAPI） | ❌ 不知道 | ❌ 不知道 |

**为什么叫"反向"？**
- 客户端**不知道**代理的存在
- 客户端**以为**直接访问的就是目标服务器
- 代理是**服务器端配置**的

**解决什么问题？**
- 隐藏后端服务
- HTTPS/SSL 终止
- 负载均衡
- 统一入口

---

### 对比表

| 对比 | 正向代理 | 反向代理 |
|------|---------|---------|
| 代理谁 | 代理客户端 | 代理后端服务器 |
| 谁主动配置 | 客户端配置 | 服务器端配置 |
| 客户端知道代理吗？ | ✅ 知道 | ❌ 不知道 |
| 后端知道真实客户端吗？ | ❌ 不知道 | ❌ 不知道 |
| 典型场景 | 翻墙、匿名访问 | 负载均衡、HTTPS 终止 |
| 典型软件 | Squid、Shadowsocks | Nginx、HAProxy |

## 三、Nginx 到底是什么？

### 概念区分

| 概念 | 是什么 | 例子 |
|------|--------|------|
| **服务器（硬件）** | 一台物理机器 | 阿里云 ECS |
| **操作系统** | 运行在硬件上的系统 | Ubuntu Linux |
| **Web 服务器（软件）** | 处理 HTTP 请求的程序 | Nginx、Apache |
| **代理服务器（软件）** | 替别人转发请求的程序 | Nginx、Squid |

### 你的项目中的层级

```
阿里云 ECS（服务器硬件）
    ↓
Ubuntu Linux（操作系统）
    ↓
Nginx（软件，运行在 OS 上）
    ↓
Docker（软件，运行在 OS 上）
    ↓
FastAPI Container（容器，运行在 Docker 上）
    ↓
FastAPI（Python 应用，运行在容器内）
```

**Nginx ≠ 服务器硬件**

Nginx 是一个**软件程序**，运行在服务器上，就像你电脑上的 Chrome、微信一样。

## 四、为什么 Nginx 可以作为反向代理？

### Nginx 的核心能力

1. **接收 HTTP 请求**：能监听端口，接收浏览器发来的请求
2. **解析 HTTP 协议**：能理解 URL、Header、Method 等
3. **建立新连接**：能作为客户端去连接后端服务
4. **转发请求**：能把原请求转发给后端
5. **返回响应**：能把后端响应返回给原客户端

### `proxy_pass` 解析

```nginx
location /api/ {
    proxy_pass http://127.0.0.1:8000;
}
```

| 配置 | 含义 |
|------|------|
| `location /api/` | 匹配所有以 `/api/` 开头的 URL |
| `proxy_pass` | 反向代理指令 |
| `http://127.0.0.1:8000` | 后端服务地址 |

### 完整请求流程

```
第一步：用户访问
    https://api.seplume.com/api/users

第二步：DNS 解析
    api.seplume.com → 106.14.206.226

第三步：请求到达 ECS
    106.14.206.226:443

第四步：Nginx 接收 HTTPS 请求
    解密 TLS → 得到 HTTP 请求

第五步：Nginx 匹配 location
    URL: /api/users
    匹配: location /api/ ✅

第六步：Nginx 转发给 FastAPI
    proxy_pass http://127.0.0.1:8000
    Nginx 作为客户端，连接 127.0.0.1:8000

第七步：FastAPI 处理并返回
    FastAPI 查询数据库
    返回: {"id": 1, "name": "张三"}

第八步：Nginx 返回给用户
    Nginx 收到 FastAPI 响应
    返回给用户浏览器
```

## 五、反向代理的核心：两个独立的连接

```
连接①：浏览器 ←→ Nginx
    - 浏览器发起
    - Nginx 接收
    - 可能是 HTTPS（加密）

连接②：Nginx ←→ FastAPI
    - Nginx 发起（Nginx 变成客户端）
    - FastAPI 接收
    - 通常是 HTTP（明文）
```

**Nginx 不是简单地"改地址"**，而是：

1. 作为**服务器**接收浏览器请求
2. 作为**客户端**向 FastAPI 发请求
3. 把 FastAPI 的响应返回给浏览器

### 类比

```
你去餐厅吃饭
    ↓
你点单给服务员（连接①）
    ↓
服务员把单子给厨房（连接②）
    ↓
厨房做好给服务员
    ↓
服务员把菜端给你
```

你不知道厨房在哪，你只和服务员交互。

## 六、为什么用 127.0.0.1:8000？

### 127.0.0.1 是什么？

`127.0.0.1` 是 **loopback 地址**，也叫 localhost。

```
127.0.0.1 = "我自己"
```

任何程序访问 `127.0.0.1`，都是在**本机内部通信**，不会经过网卡出去。

### 你的项目中的网络拓扑

```
阿里云 ECS（一台机器）
    │
    ├── Nginx（运行在宿主机）
    │       ↓
    │   访问 127.0.0.1:8000
    │       ↓
    │   "找本机的 8000 端口"
    │
    └── Docker
            ↓
        FastAPI Container
            ↓
        端口映射: 127.0.0.1:8000 → 容器内:8000
```

### Docker 端口映射

```yaml
ports:
  - "127.0.0.1:8000:8000"
```

含义：

```
宿主机 127.0.0.1:8000  ←→  容器内 :8000
```

**效果**：
- 宿主机上任何程序访问 `127.0.0.1:8000` → 自动转发到容器内的 8000 端口
- 外部机器无法直接访问（因为绑定的是 `127.0.0.1`，不是 `0.0.0.0`）

### 可选的地址对比

| 地址 | 含义 | 谁能访问 | 安全性 |
|------|------|---------|--------|
| `127.0.0.1:8000` | 仅本机访问 | 只有 ECS 上的程序 | ✅ 最安全 |
| `0.0.0.0:8000` | 所有网卡 | ECS 上程序 + 外部直接访问 | ⚠️ 不安全 |
| `172.17.0.x:8000` | Docker 内部 IP | 同一 Docker 网络的容器 | ✅ 安全 |

### 为什么选择 127.0.0.1？

```
用户
    ↓
Nginx（宿主机）
    ↓
127.0.0.1:8000（本机转发）
    ↓
Docker 端口映射
    ↓
FastAPI Container
```

**好处**：
1. **安全**：外部无法直接访问 FastAPI，必须经过 Nginx
2. **简单**：Nginx 在宿主机，FastAPI 通过端口映射暴露到宿主机
3. **隔离**：FastAPI 不直接暴露给公网

## 七、为什么生产环境需要 Nginx 反向代理？

### 方案 A：直接暴露 FastAPI

```
用户
    ↓
http://公网IP:8000
    ↓
FastAPI
```

### 方案 B：Nginx 反向代理

```
用户
    ↓
https://api.seplume.com:443
    ↓
Nginx
    ↓
http://127.0.0.1:8000
    ↓
FastAPI
```

### 对比

| 能力 | 直接暴露 FastAPI | Nginx 反向代理 |
|------|-----------------|---------------|
| 隐藏后端服务 | ❌ 用户直接看到 :8000 | ✅ 用户看不到后端 |
| HTTPS/SSL | ❌ FastAPI 不擅长 | ✅ Nginx 专业处理 |
| 统一入口 | ❌ 多个服务多个端口 | ✅ 一个域名统一入口 |
| 负载均衡 | ❌ 不支持 | ✅ 可以分发到多个后端 |
| 静态资源 | ❌ FastAPI 不擅长 | ✅ Nginx 高效处理 |
| 超时控制 | ⚠️ 应用层控制 | ✅ Nginx 层控制 |
| 请求体限制 | ⚠️ 应用层控制 | ✅ Nginx 层拦截 |
| 限流 | ⚠️ 应用层实现 | ✅ Nginx 层限流 |

## 八、端口在反向代理中的作用

### 端口是什么？

端口是**服务标识符**，告诉操作系统"这个请求应该交给哪个程序"。

### 你的项目中的端口

| 端口 | 谁监听 | 协议 | 谁访问 |
|------|--------|------|--------|
| **443** | Nginx | HTTPS | 用户浏览器 |
| **80** | Nginx | HTTP | 用户浏览器 |
| **8000** | FastAPI | HTTP | 只有 Nginx（127.0.0.1） |

### 为什么可以同时存在？

因为它们**监听不同的端口**：

```
Nginx 监听: 443
FastAPI 监听: 8000

用户访问 443 → Nginx 处理
Nginx 转发 8000 → FastAPI 处理
```

操作系统通过端口区分不同的服务。

## 九、完整请求追踪

### 用户访问 `https://api.seplume.com/users/123`

```
① DNS
    浏览器查询: api.seplume.com 的 IP
    DNS 返回: 106.14.206.226

② TCP 三次握手
    浏览器 → 106.14.206.226:443
    TCP 连接建立

③ TLS 握手
    协商加密密钥
    TLS 加密通道建立

④ HTTP 请求（在 TLS 加密通道中）
    GET /users/123 HTTP/1.1
    Host: api.seplume.com

⑤ Nginx 接收请求
    解密 TLS → 得到 HTTP 请求

⑥ 匹配 server 块
    server_name api.seplume.com ✅

⑦ 匹配 location
    location / {
        proxy_pass http://127.0.0.1:8000;
    }

⑧ proxy_pass 转发
    Nginx 建立新连接到 127.0.0.1:8000
    发送: GET /users/123

⑨ Docker 端口映射
    宿主机 127.0.0.1:8000 → 容器内 :8000

⑩ FastAPI 处理
    查询数据库
    返回: {"id": 123, "name": "张三"}

⑪ 返回响应
    FastAPI → Nginx → 浏览器
```

### 完整通信图

```
浏览器
   │
   │ HTTPS (加密)
   │ TCP: 106.14.206.226:443
   ↓
 Nginx
   │
   │ HTTP (明文)
   │ TCP: 127.0.0.1:8000
   ↓
Docker Container
   │
   ↓
FastAPI :8000
   │
   ↓
PostgreSQL / Redis
```

|------|------|----------------|

## 十一、最终认知总结

### 一句话总结

| 概念 | 一句话总结 |
|------|-----------|
| **Proxy 是什么？** | 替别人完成请求的中间人 |
| **Forward Proxy 是什么？** | 客户端主动使用的代理，代理客户端访问外网 |
| **Reverse Proxy 是什么？** | 服务器端配置的代理，代理后端服务对客户端透明 |
| **Nginx 是什么？** | 运行在服务器上的 HTTP 处理软件 |
| **Nginx 为什么能做 Reverse Proxy？** | 它能接收 HTTP 请求，再作为客户端请求后端，然后把响应返回 |
| **`proxy_pass` 是什么？** | Nginx 的反向代理指令，告诉 Nginx 把请求转发给哪个后端 |
| **FastAPI 在整个架构中是什么？** | 真正的业务服务器，处理业务逻辑，被 Nginx 代理 |
| **为什么用 127.0.0.1？** | Nginx 和 FastAPI 在同一台机器上，127.0.0.1 是本机通信 |

### 最终认知

```
Nginx 不是"神秘的中间层"

它本质上是一个运行在服务器上的软件。

它可以接收客户端请求，
再作为客户端去请求后端服务，
然后把后端响应返回给原客户端。

因此：

客户端 → Nginx → 后端

就是典型的反向代理架构。
```

## 十二、面试回答模板

### 1 分钟解释 Nginx 反向代理

> "Nginx 反向代理就是客户端和后端服务器之间的中间人。
>
> 用户访问 `https://api.seplume.com` 时，实际上连接的是 Nginx，Nginx 接收请求后，再作为客户端去请求后端的 FastAPI，然后把 FastAPI 的响应返回给用户。
>
> 对用户来说，它以为直接访问的就是 API 服务器，完全不知道后端 FastAPI 的存在。这就是'反向'的含义——代理是服务器端配置的，客户端不知道它的存在。
>
> 这样做的好处是：隐藏后端服务、统一 HTTPS 入口、可以做负载均衡、限流、缓存等。"

### 为什么用 127.0.0.1:8000？

> "因为 Nginx 和 FastAPI 在同一台 ECS 服务器上。127.0.0.1 是 loopback 地址，代表本机。
>
> Docker 通过端口映射把容器内的 8000 端口映射到宿主机的 127.0.0.1:8000，这样 Nginx 就能通过本机地址访问 FastAPI。
>
> 这样做的好处是 FastAPI 不直接暴露给公网，外部必须经过 Nginx 才能访问后端服务，提高了安全性。"
